# Unix Pipeline — конкурентный конвейер обработки данных на Go

Учебный проект на Go, реализующий конкурентную обработку данных по принципу Unix Pipeline.

Конвейер состоит из независимых этапов, которые выполняются параллельно и передают результаты друг другу через Go-каналы.

На примере обработки электронной почты реализованы получение пользователей, удаление дубликатов, пакетное получение сообщений, проверка на спам и сортировка результатов.

Основная цель проекта — практическое применение goroutines, channels, WaitGroup, Mutex и ограничение конкурентного доступа к внешним сервисам.

## Возможности

- Построение конвейера из произвольного количества этапов.
- Потоковая передача данных между этапами через каналы.
- Параллельное выполнение независимых операций.
- Удаление дубликатов пользователей.
- Пакетная обработка запросов (batching).
- Ограничение количества одновременных запросов с помощью семафора.
- Синхронизация goroutines через `sync.WaitGroup`.
- Защита общих данных через `sync.Mutex`.
- Сбор и сортировка результатов.
- Автоматическое тестирование конкурентной обработки.

## Архитектура

Конвейер обработки сообщений:

```text
        Email addresses
               |
               v
        +-------------+
        | SelectUsers |
        +-------------+
               |
               | User
               v
       +----------------+
       | SelectMessages |
       +----------------+
               |
               | MsgID
               v
        +-------------+
        |  CheckSpam  |
        +-------------+
               |
               | MsgData
               v
       +----------------+
       | CombineResults |
       +----------------+
               |
               v
        Sorted results
```

Каждый этап получает данные через входной канал и передаёт обработанные результаты в выходной.

Этапы выполняются конкурентно: следующий этап может начать обработку до завершения предыдущего.

## Этапы конвейера

### 1. SelectUsers

Получает email-адреса и преобразует их в пользователей с помощью `GetUser`.

Для каждого email запускается отдельная goroutine.

Поскольку несколько email могут соответствовать одному пользователю, выполняется удаление дубликатов по `User.ID`.

Для синхронизации используются:

- `sync.WaitGroup` — ожидание завершения goroutines.
- `sync.Mutex` — защита `map` с уже обработанными пользователями.

### 2. SelectMessages

Получает пользователей и запрашивает список их сообщений через `GetMessages`.

Внешний API поддерживает пакетные запросы с ограничением на количество пользователей в одном батче.

Реализовано:

- Формирование батчей пользователей.
- Параллельная обработка батчей.
- Передача полученных `MsgID` следующему этапу.

В текущей конфигурации максимальный размер батча — 2 пользователя.

### 3. CheckSpam

Проверяет сообщения на спам через функцию `HasSpam`.

Внешний антиспам-сервис ограничивает количество одновременно выполняемых запросов.

Для соблюдения ограничения используется семафор на базе буферизированного канала:

```go
sem := make(chan struct{}, HasSpamMaxAsyncRequests)
```

Перед запуском проверки занимается место в семафоре, после завершения — освобождается.

Это позволяет выполнять проверки параллельно, не превышая допустимое число одновременных запросов.

В текущей конфигурации максимум — 5 одновременных проверок.

### 4. CombineResults

Собирает результаты проверки сообщений и сортирует их.

Порядок сортировки:

1. Сначала сообщения с `HasSpam = true`.
2. Затем сообщения с `HasSpam = false`.
3. Внутри каждой группы — по возрастанию `MsgID`.

Результат преобразуется в строки формата:

```text
true 221945221381252775
true 357347175551886490
false 26236336874602209
false 59892029605752939
```

## Работа RunPipeline

Функция `RunPipeline` принимает произвольное количество этапов:

```go
type cmd func(in, out chan interface{})
```

Для связи между этапами создаются каналы.

Каждый промежуточный этап запускается в отдельной goroutine.

После завершения этапа его выходной канал закрывается, чтобы следующий этап мог корректно завершить чтение.

Последний этап выполняется синхронно, поэтому `RunPipeline` возвращает управление после завершения конвейера.

## Моделирование внешних сервисов

В проекте используются функции, имитирующие обращения к внешним системам:

| Функция | Назначение | Время выполнения |
|---|---|---|
| `GetUser` | Получение пользователя по email | ~1 секунда |
| `GetMessages` | Получение сообщений пользователей | ~1 секунда |
| `HasSpam` | Проверка сообщения на спам | ~100 мс |

Задержки моделируются через `time.Sleep`.

Реальные HTTP-запросы и подключения к базам данных в проекте не используются.

Такая модель позволяет проверить эффективность конкурентного выполнения и соблюдение ограничений внешних API.

## Тестирование

Тесты проверяют:

- Потоковую передачу данных между этапами.
- Конкурентное выполнение конвейера.
- Корректное завершение всех этапов.
- Отсутствие дубликатов пользователей.
- Обработку email-алиасов.
- Независимость параллельно запущенных конвейеров.
- Правильность итоговых результатов.
- Количество вызовов внешних функций.
- Соблюдение ограничений по времени выполнения.

### Запуск тестов

```bash
go test ./...
```

### Проверка на data race

```bash
go test -race ./...
```

Race detector помогает обнаруживать небезопасный конкурентный доступ к общей памяти.

### Проверка покрытия

```bash
go test -cover ./...
```

Некоторые тесты проверяют время выполнения, поэтому результаты могут зависеть от производительности и загруженности компьютера.

## Чему посвящён проект

Проект демонстрирует практические приёмы конкурентного программирования на Go:

- Организация потоковой обработки данных.
- Передача данных между goroutines через каналы.
- Синхронизация конкурентных операций.
- Безопасная работа с общим состоянием.
- Batch processing.
- Ограничение конкурентности с помощью семафоров.
- Тестирование конкурентного кода.

## Ограничения

Проект является учебным.

Внешние сервисы моделируются локальными функциями, а не реальными сетевыми запросами.

Обработка ошибок на отдельных этапах упрощена: при ошибке получения сообщений или антиспам-проверки соответствующий результат пропускается.

В проекте не реализованы отмена конвейера через `context.Context` и ограничение количества goroutines на этапе получения пользователей.
